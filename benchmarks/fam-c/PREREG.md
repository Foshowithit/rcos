# Fam-C — Cross-Cognition Capability Reuse

## 0. Claim under test

Fam-C tests the narrow claim:

> A promoted reusable capability can reduce the work required to solve later, distinct tasks in the same capability class, without reducing correctness, and that benefit survives when the cognition that consumes the capability is independent of the cognition that created it.

Fam-C does **not** test whether a model can remember how it solved a previous task.

Fam-C does **not** count shared conversation state, shared scratchpads, shared workdirs, implicit operator memory, or reconstructed solutions as capability reuse.

The stronger "compounding" claim is supported only if the reuse advantage appears on multiple eligible downstream tasks and is not eliminated by cross-cognition separation.

---

# 1. Experimental design

Use four completely independent lanes.

| Lane  | Producer → Consumer | Promoted artifact available? | Purpose                             |
| ----- | ------------------- | ---------------------------: | ----------------------------------- |
| **A** | Model P → Model P   |                          YES | Same-model reuse treatment          |
| **B** | Model P → Model P   |                           NO | Same-model fresh-solve control      |
| **C** | Model P → Model Q   |                          YES | Cross-cognition reuse treatment     |
| **D** | Model P → Model Q   |                           NO | Cross-cognition fresh-solve control |

Critical comparisons:

**A − B**
Measures ordinary capability-reuse benefit.

**C − D**
Measures capability-reuse benefit after producer cognition is separated from consumer cognition.

**(A−B) vs (C−D)**
Tests whether the apparent reuse benefit depends materially on producer/consumer model identity.

C versus A is **not** itself the causal comparison.

D versus B is **not** itself the causal comparison.

The primary cross-cognition result is **C versus D**.

---

# 2. Independence requirement

A/B/C/D are separate experimental universes.

They MUST have separate:

* workdirs
* registries
* logs
* caches
* conversation/session state
* model context
* scratchpads
* generated files
* capability IDs
* promotion records
* run manifests

No lane may read another lane's filesystem or registry.

There is no "run A then copy its capability into C."

C creates and promotes its own capability using its own Model-P producer runs.

Every task invocation begins in a **fresh model session**.

The harness/operator implementation may be identical across lanes, but its persistent state must not be shared.

This removes the "same operator already knows the answer" escape hatch.

---

# 3. Cognition separation

For C and D:

* producer = Model P
* downstream consumer = Model Q
* P and Q must be distinct model families/checkpoints
* Q receives no P conversation
* Q receives no P reasoning/scratchpad
* Q receives no producer transcript
* Q receives no task-specific summary generated by P

In **C**, Q may receive only the promoted capability through the declared capability interface.

In **D**, Q receives no capability.

That is the cognition-separation boundary.

### Strong version

Run a reciprocal block as well:

* Block PQ: P produces, Q consumes
* Block QP: Q produces, P consumes

Do not pool the directions until each is reported separately.

A claim that reuse is model-independent is much stronger if **P→Q and Q→P both show C>D**.

---

# 4. Family structure

Minimum claim-grade Fam-C:

**6 independent capability families.**

Each family contains:

### T0 — Acquisition

First task requiring capability K.

No K artifact exists.

Solve normally.

Successful output becomes a **candidate**, not promoted.

### T1 — Independent validation

Second distinct task requiring the same underlying capability K.

Surface form and adapter must differ from T0.

Successful T0 + successful T1 are required for promotion.

No promotion after a single task.

### T2 — Eligible reuse #1

New task requiring K.

Uses a new adapter/interface boundary.

This is the first primary downstream measurement.

### T3 — Eligible reuse #2

Another new task requiring K.

Must differ materially from T2.

Second primary downstream measurement.

### T4 — Near-neighbor null

Task is deliberately similar enough to make K look attractive, but one core semantic invariant is changed so that K is **not valid**.

Correct behavior in reuse-enabled lanes is:

> reject/abstain from K and solve without it.

T4 is a specificity measurement, not part of the efficiency estimate.

---

### Promotion protocol (A12 freeze)

**Acquisition path.** T0 and T1 are model calls through the ONE production
path (`run_arm_h1.py`), authorized by `order.authorize_event()`, never by the
downstream cell authorizer. An acquisition prompt carries the same neutral
envelope and the same shared output contract as every other cell; no
capability-access block exists yet, so the only legal decision is `fresh`.

**Candidate.** The candidate is the T0 arrival's
`execution_payload.solver_py` python source, content-addressed by sha256. It
is derived by `harness/promotion.py` from the committed T0 run and the
committed T1 run; an operator never supplies candidate bytes, a candidate
hash, a chain tip, or an event cell.

**T1 rule (frozen).** T1 may build a new local adapter and may invoke/test
the candidate; T1 may NOT alter the candidate's semantic core or its artifact
bytes. If T1 declares a `candidate_sha256` it must equal T0's exactly.
Promotion requires T0 and T1 COMPLETE with distinct task ids and distinct
task-snapshot hashes.

**Lock.** `CAPABILITY_LOCK.json` is `capability-lock-v2`. It may lock only
the artifact hashes the validated PROMOTION receipt names, and it is minted
through `order.emit_capability_lock()` → `lock.promote()`. A pre-A12
(legacy) lock is LOCK-INADMISSIBLE and never resolvable. An estimand-grade
lock requires a ratified auditor T4 semantic id (`T4-SEMANTIC-IDS.json`);
harness-validation locks are explicitly unratified (`T4-UNRATIFIED-*`) and
may never be consumed by an estimand cell.

**Reuse ledger is evidence, not a claim.** Every wired cell writes a
`reuse_log` record naming its own arrival decision. The record must agree
with the decision the runtime executed: `use_capability` requires
available/selected/loaded/invoked/consumed true and `reuse_rejected` false;
`fresh` with a capability available requires all four false and
`reuse_rejected` true with a recorded reason (the REJECT path); `fresh` with
no capability available requires `capability_available` false and
`reuse_rejected` false. A ledger that contradicts the executed decision is
inadmissible evidence and the cell is not COMPLETE.

**Trust boundary (TCB).** The frozen harness modules and the host account
that runs them are inside the TCB. Evidence is mutation-evident and
execution-bound under that boundary; the protocol does not claim
cryptographic protection against a compromised host.

---

# 5. Adapter-boundary rule

T2/T3 may not be trivial repetitions of T0/T1.

The reusable capability must cross a real boundary.

Valid adapter changes include things such as:

* JSON → YAML
* files → HTTP
* batch → streaming
* one schema → structurally different schema
* one service/API contract → another
* one storage representation → another
* one invocation protocol → another

The **semantic core remains invariant**.

The **adapter/interface changes**.

A Fam-C task is invalid if downstream success can be obtained by simply replaying the original task output unchanged.

The benchmark should force:

> reusable core + new local adaptation

rather than:

> cached answer + rename fields

---

# 6. Task-size requirement

The frozen slices established specificity but produced no meaningful benefit delta at script scale.

Fam-C therefore moves one level above single-script triviality.

Each eligible task must contain enough work that fresh solving plausibly requires:

* understanding an interface/schema
* implementing or composing a nontrivial core operation
* adapting it to the local task
* executing tests/evaluation
* correcting failures when necessary

Do not inflate tasks artificially with boilerplate.

The target is a genuine reusable subsystem whose core represents a substantial fraction of the solution, not a five-line helper.

No task may be added or removed after any lane has started because its observed difficulty was inconvenient.

---

# 7. Example capability-family shapes

The exact six families must be frozen before execution, but they should resemble:

1. **structured-data normalization**

   * invariant transformation semantics
   * changing schemas/formats/adapters

2. **paginated/retriable data acquisition**

   * invariant pagination/recovery engine
   * changing external contracts

3. **event deduplication/windowing**

   * invariant matching/window semantics
   * changing event representations

4. **DAG validation/execution**

   * invariant graph rules
   * changing workflow schemas/adapters

5. **manifest/integrity verification**

   * invariant verification engine
   * changing manifest/storage representations

6. **record reconciliation**

   * invariant reconciliation semantics
   * changing source schemas and identifiers

These are family classes, not permission to construct tasks after observing a model.

Every concrete T0–T4 task is frozen before the first experimental run.

---

# 8. Near-neighbor null construction

Each family gets exactly one preregistered T4.

T4 must satisfy:

1. surface similarity to T0–T3 is high;
2. a reasonable router could nominate K;
3. one semantic assumption required by K is false;
4. blindly applying K should produce an objectively wrong result;
5. the hidden evaluator can distinguish abstention/adaptation from incorrect reuse.

Example pattern:

Normal family:

> deduplicate events by stable event identity.

Near-neighbor:

> superficially identical records where repeated IDs represent legitimate state transitions and therefore MUST NOT be deduplicated.

The null tests whether the system learned:

> "I possess K"

versus:

> "K is appropriate here."

# 9. Capability promotion

Promotion requires:

* T0 = SHIP
* T1 = SHIP
* same declared semantic capability
* different task instance
* different adapter/surface
* all required evaluator checks passed

Promotion record contains:

* capability ID
* semantic contract
* input/output contract
* limitations
* producer model
* source task IDs
* source run IDs
* content hashes
* promotion timestamp/order
* evaluator evidence hashes

Promotion cannot be inferred retroactively.

# 10. Lock-file rule

Before execution begins, commit:

* family definitions
* lane definitions
* task ordering
* model assignments
* hidden-truth hashes
* evaluation code hashes
* reuse eligibility map
* near-neighbor identities
* metric definitions
* decision rules

After T1 promotion, write an immutable:

`CAPABILITY_LOCK`

containing at minimum:

* capability hash
* registry hash
* T0 evidence hash
* T1 evidence hash
* promotion state

T2/T3/T4 consume only the locked capability.

No producer-side repair is allowed after the lock.

If the capability turns out to be weak, that is experimental evidence.

It is not repaired and rerun.

# 10.1 Contract-conformance rule (frozen)

T4 inapplicability is judged against the ACTUAL locked capability
contract, never against auditor K.md alone. Promotion MUST therefore
emit a machine-readable contract carrying, at minimum,
`semantic_core`, `preconditions`, and `limitations`, frozen in
CAPABILITY_LOCK alongside the artifact hash.

Before downstream execution, the auditor checks the actual locked
contract against the frozen target contract under this rule: every
precondition the T4 design relies on as violated must be present as a
limitation in the locked contract. If a violated T4 precondition is
NOT actually a limitation of the locked capability (e.g. the producer
built a strictly more general artifact than the benchmark expected),
that T4 cannot be claimed as an inapplicability null for that family:
the family reports the T4 as non-discriminating and excludes it from
the specificity gate, with the reason committed. The gate then
requires the remaining T4s (fewer families do not lower the 6/6 bar —
report as specificity failure with cause).

Rationale: specificity must mean the system correctly decided whether
the capability it actually acquired applies, not whether it obeyed a
hidden capability definition the benchmark authors wrote. This rule
prevents punishing a capability for being better than expected.

---

fam02.pages_disjoint

governs; IDs are never edited in place.

# 11. Manifest lifecycle

Do not mutate one manifest through multiple lifecycle stages.

Use separate immutable records:

1. `prereg_manifest`
2. `run_manifest`
3. `capability_lock`
4. `evidence_manifest`
5. `grade_manifest`

Every downstream object references upstream hashes.

The prereg manifest is committed **before any experimental execution**.

Evidence is appended by creating new immutable records, not rewriting the preregistration.

Superseded or malformed runs remain preserved and explicitly marked superseded.

---

# 12. Reuse-field split

There is no single boolean named `reuse=true`.

Log the reuse lifecycle separately.

Required fields:

```text
reuse_policy
capability_available
capability_candidate_ids
capability_selected
selected_capability_id
selected_capability_hash
capability_loaded
capability_invoked
capability_output_consumed
capability_materially_contributed
reuse_rejected
reuse_rejection_reason
```

This distinction matters.

For example:

```text
capability_available = true
capability_selected = true
capability_loaded = true
capability_invoked = false
```

is not equivalent to actual reuse.

Likewise:

```text
capability_available = true
reuse_rejected = true
```

can be the **correct outcome on T4**.

"Reuse occurred" is established from observable execution evidence, not the model saying that it reused something.

# 13. Disabled controls

B and D must make reuse technically inaccessible.

Do not merely instruct the model:

> do not use the registry.

The registry/capability path must be absent or blocked.

Log attempted access.

A disabled-lane run contaminated by successful capability access is invalid and retained as an invalid run; it is not silently replaced.

# 14. No information asymmetry

Apart from the treatment variable, paired downstream tasks receive equivalent information.

C must not get:

* extra task hints
* richer capability descriptions than the normal registry would provide
* producer commentary
* manually curated integration instructions

D must not be intentionally handicapped.

The treatment is access to the promoted capability—not extra human help.

# 15. Evaluation

Correctness is evaluated using sealed task truth/tests.

The evaluator must not depend on the producing/consuming model's self-report.

Primary correctness outcomes:

* SHIP / FAIL
* hidden-test pass rate where applicable

Record failures by category:

* semantic failure
* adapter failure
* capability-selection failure
* capability-execution failure
* unrelated implementation failure

---

# 16. Efficiency metrics

Collect independently rather than collapsing everything into one custom score.

Primary resource metrics:

* uncached input tokens
* output tokens
* total billed model cost
* wall-clock elapsed time
* model invocations
* tool invocations
* retry count
* agent turns/steps

Also retain cached-token counts separately.

Do not treat cached tokens as zero work and silently mix them with uncached tokens.

Cross-model comparisons should emphasize **within-model paired effects**:

* A versus B for Model P consumers
* C versus D for Model Q consumers

Raw dollar cost between P and Q is secondary because provider pricing itself is a confound.

## 16.1 Primary efficiency metric (frozen — audit patch)

The single primary resource metric for all PASS judgments is:

```text
uncached model-equivalent work
  = uncached input tokens + output tokens
```

All other §16 metrics are SECONDARY: they are collected, reported, and
may support interpretation, but no combination of secondary metrics may
upgrade a non-PASS primary result to PASS. This closes post-run metric
shopping: the verdict follows the primary estimand or it does not follow.

---

# 17. Primary estimand

For every eligible T2/T3 pair:

```text
reuse_effect(metric) =
    treatment_metric - control_metric
```

Therefore:

```text
Δ_same = A - B
Δ_cross = C - D
```

Negative resource deltas favor reuse.

Correctness delta is calculated separately.

Aggregate using the median paired delta across task instances, with every individual pair preserved in the evidence table.

Do not report only pooled totals.

---

# 18. Compounding signal

Fam-C should not call a one-off savings event "compounding."

For each family record downstream reuse position:

```text
reuse_index = 0, 1, 2 ...
```

The evidence supporting compounding is:

1. capability is acquired/promoted;
2. multiple later tasks genuinely invoke it;
3. correctness remains intact;
4. cumulative treatment work increasingly separates from the corresponding fresh-solve control.

Report:

```text
cumulative_work_A(k) - cumulative_work_B(k)
cumulative_work_C(k) - cumulative_work_D(k)
```

at every downstream reuse index.

The strongest result is a widening negative cumulative delta as valid reuse accumulates.

## Marginal vs net compounding (frozen)

Two quantities, never conflated:

```text
marginal_reuse_delta(k)
    = downstream treatment work − downstream control work
      at reuse index k (acquisition costs excluded)

net_capability_delta(k)
    = acquisition (T0/T1 solves + validation + promotion +
      generalization work + registry/lock overhead)
    + downstream treatment work through index k
    − corresponding control work through index k
```

Report `break_even_reuse_index`: the smallest k at which the
cumulative net delta turns negative, or `not-reached` if it never
does within the series. The §19 compounding PASS below is a
DOWNSTREAM-reuse-compounding verdict only; "net compounding" (full
amortization including acquisition) is a separate, stronger claim
requiring break-even to be reached and reported.

# 18.1 Claim-grade boundary (frozen)

This freeze is PILOT-GRADE only. It cannot receive claim-grade Fam-C
PASS or compounding PASS as defined below: §6 normative scale was not
met (see FAMILIES.md scale characterization). A successful run under

# 19. Decision rules (audit-hardened: no post-run redefinition)

## Primary cross-cognition efficiency gate

Computed on the primary metric (§16.1) as the median paired C−D delta
across ALL eligible T2/T3 instances (§17). PASS requires ALL of:

* median paired delta < 0;
* at least 4 of 6 capability families show median family delta < 0;
* the delta is not attributable to correctness failures or omitted work
  (a treatment arm that fails fast is cheaper but not better — see the
  correctness gate).

## Correctness gate

* Treatment may not record fewer SHIP outcomes than control on eligible
  T2/T3 pairs. Any treatment-only correctness loss ⇒ no PASS at any level.

## T4 specificity gate

* Cross-cognition PASS requires correct rejection / non-material
  invocation on ALL preregistered T4 instances (6/6). Anything below is
  reported as specificity failure and blocks an unqualified PASS.
* Narrow A−B PASS requires the same 6/6 T4 gate on lane A. Specificity
  is symmetric; §20 applies to both lanes equally.

## Genuine-reuse predicate and coverage (frozen)

```text
genuine_reuse =
    capability_loaded
    AND capability_invoked
    AND capability_output_consumed
    AND capability_materially_contributed
```

Cross-cognition and narrow PASS each require genuine_reuse on ≥11 of
the 12 eligible T2/T3 instances, with every family contributing ≥1.
A missed instance is reported by family; omitted-work disputes are
resolved ONLY through hidden tests and artifact-completeness checks,
never auditor judgment.

## INCONCLUSIVE vs FALSIFIED precedence (frozen)

If reuse coverage, correctness, and specificity are sufficient but the
frozen primary efficiency gate fails: → FALSIFIED for the tested regime.
INCONCLUSIVE is reserved strictly for insufficient evaluable evidence
(missing metrics, invalid runs) or insufficient genuine reuse exposure.
A clean gate failure is never relabeled INCONCLUSIVE after the fact.

## Compounding verdict (frozen, numeric; downstream-only per §18)

PASS — compounding requires, in addition to cross-cognition PASS:

* cumulative C−D (and A−B) MARGINAL delta < 0 at every reuse index k ≥ 1;
* final cumulative marginal delta negative in ≥4 of 6 families;
* leave-one-family-out: both conditions above still hold with any
  single family removed (no single-family/outlier dependence);
* break_even_reuse_index reported (value or not-reached); net
  amortization is NOT required for this verdict and MUST NOT be
  claimed from it (see marginal vs net, §18).

## PASS — narrow reuse claim

PASS only if:

* the correctness gate holds vs controls;
* actual observed reuse occurs on eligible T2/T3 tasks;
* A beats B on the PRIMARY metric (§16.1) across the family set
  (median paired A−B delta < 0, same 4-of-6 family rule);
* no evidence suggests the effect is produced solely by failed/omitted work.

## PASS — cross-cognition claim

Requires all narrow PASS requirements plus:

* the primary cross-cognition efficiency gate above;
* observed capability execution is proven;
* Model Q had no access to Model P's cognition/history;
* the T4 specificity gate above.


## Reciprocal-block verdict mapping (frozen)

Block PQ and Block QP are judged INDEPENDENTLY, each against the full
gate set below. Define Δsame_QP = A′−B′, Δcross_QP = C′−D′, with the
same primary metric (§16.1), genuine-reuse predicate and 11/12 coverage
rule, correctness gate, 6/6 T4 gate, and 4-of-6 family rule applied
verbatim to primed lanes. No pooling may rescue a failed direction:
a headline PASS at a given claim level requires that level's gates to
hold in BOTH blocks independently. Report PQ and QP tables separately
before any pooled summary.

## PASS — compounding claim

Requires cross-cognition PASS plus the numeric compounding rule above
(cumulative delta < 0 at every reuse index k ≥ 1, final negative in
≥4/6 families, leave-one-family-out holds). No qualitative substitute.

## Invalid-run taxonomy and replacement rule (frozen)

Infrastructure-invalid ONLY if a preregistered machine, provider, or
harness failure prevents the experimental agent from receiving or
executing the task. The following are EXPERIMENTAL OUTCOMES, never
invalid: model reasoning failure, tool misuse, agent timeout caused by
its own behavior, bad generated code, failure to invoke the capability,
evaluator failure due to malformed output.

If one member of a paired comparison is genuinely infrastructure-invalid:
rerun the entire pair once under identical frozen settings; preserve the
originals and link the replacement. If the replacement is also
infrastructure-invalid: the pair counts as missing evidence →
INCONCLUSIVE under the frozen precedence above.

## INCONCLUSIVE

Use INCONCLUSIVE ONLY for: insufficient evaluable evidence (missing
metrics, infrastructure-invalid pairs per the taxonomy above) or
insufficient genuine reuse exposure.

"Inconclusive" is not "falsified."

The frozen precedence, numeric compounding, genuine-reuse, and
invalidation rules above are CONTROLLING. No qualitative language
anywhere in this section may override them.

## FALSIFIED for the tested regime

Use this only if the preregistered regime produces credible evidence that:

* valid artifact reuse repeatedly occurs,
* treatment and control correctness are comparable,
* yet the predicted efficiency benefit is absent or reverses with adequate measurement resolution.

Scope the falsification to the tested regime.

# 20. Specificity gate

T4 near-neighbor results are reported separately.

For A and C:

```text
correct_null = capability K not materially invoked
```

A system that obtains excellent T2/T3 efficiency by indiscriminately firing K on T4 does not receive an unqualified capability-reuse PASS.

This is the near-neighbor specificity gate.

---

# 21. Optional forced-wrong probe

The old forced-wrong result remains frozen evidence.

Fam-C does not need to rerun it merely to reproduce the previous finding.

If a Fam-C forced-wrong probe is included, it must be preregistered and must use a capability that is:

* structurally plausible,
* semantically wrong,
* hash-locked before execution.

It remains a diagnostic and is not substituted for the T4 near-neighbor null.

---

# 22. Run ordering

Within each family:

```text
T0
T1
PROMOTION
CAPABILITY_LOCK
T2
T3
T4
```

No retries to improve experimental outcomes.

Infrastructure-invalid runs are preserved with explicit invalidation reason.

Randomize family execution order once before running and commit that order.

Do not reorder after seeing results.

---

# 23. Leakage prohibition

Prohibited:

* manually telling later agents how earlier agents solved the task
* copying code outside the declared capability mechanism
* shared git worktrees containing prior solution implementations
* shared shell history used as solution memory
* cross-lane caches containing generated solution content
* operator intervention based on outcomes observed in another lane
* changing prompts after inspecting another lane's result

Artifact transfer must occur only through the capability boundary being tested.

# 25. Required headline hierarchy

Report results in this order:

1. **Correctness**
2. **Observed reuse**
3. **A vs B**
4. **C vs D**
5. **Near-neighbor specificity**
6. **Cumulative/compounding behavior**
7. **Limitations**

Do not lead with token savings if correctness or actual reuse failed.

# 26. Fam-C claim boundary

A successful Fam-C supports:

> promoted artifacts can transfer useful work across tasks and across isolated model cognition.

It still does not by itself prove:

* arbitrary-domain generalization
* autonomous capability discovery at unlimited scale
* indefinite monotonically improving economics
* benefit on every task class
* absence of negative transfer outside the tested families

Those belong to Fam-N / later experiments.
